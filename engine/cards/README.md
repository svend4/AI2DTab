# Картотека (прототип): обзор-каталог → карточки по id → журнал фактов

Продолжение мысли из `../CHAT-CRUTCH.md`: чат одномерен, модель между вызовами ничего не помнит, и каждый вызов заново несёт весь диалог.
Поэтому важно не то, что лежит в хранилище, а то, **что попадает в диалог**. Картотека пускает туда по ступеням «от общего к частному»,
как заголовки новостной группы (команда OVER в NNTP) или отделы магазина:

```
каталог групп        g3 | src/lib/auth | 19 cards ~27K tok | …              ← всегда в начале промпта (кэшируется)
  строки карточек    f054 | src/lib/auth/gate-identity.server.ts | 212L | … ← по одной строке на файл или реплику
    оглавление       open f054  →  §1 L12-40 function verify… (~1.1K)       ← вместо 3K+ токенов текста
      раздел/строки  open f054 section=2 | lines="120-160"                  ← только то, что нужно
```

Три вещи, которые чаще всего путают, здесь разведены:

| что | кто отвечает |
|---|---|
| **что попадёт** в диалог | каталог, `find`, `open` с оглавлением и потолком вывода |
| **сколько стоит перечитать** то, что уже в диалоге | кэш промпта на стороне провайдера (мы лишь держим начало промпта неизменным) |
| **где лежит всё остальное** | SQLite: карточки, версии, индекс FTS5, журнал фактов |

База данных не может быть «кэшем» модели (кэш — это снимок вычислений для точной последовательности токенов), но может и должна быть **памятью**:
из неё собирают маленький промпт, и в неё складывают вытесненное.

## Что внутри

Один файл без зависимостей, `cards.py` (стандартная библиотека, SQLite с FTS5):

| команда | что делает |
|---|---|
| `index-code ПУТЬ` | файлы репозитория → карточки (оглавление по `def/class/function`, заголовкам Markdown, `CREATE …`); группы = каталоги |
| `index-chat ФАЙЛ.md` | экспорт ChatGPT → карточка на каждую пару «вопрос/ответ», ветки по провалам сходства (TextTiling в малом), оглавление по заголовкам (в том числе внутри цитат `> # …`) |
| `index-pm [БАЗА]` | объекты L3 комплекта (`../project-store.sqlite`, только чтение) → карточки; группы A/B/C/D |
| `catalog [--group g3] [--level 1]` | обзор: группы, затем строки карточек группы |
| `find "слова"` | поиск BM25 по кускам; «все слова», затем «любое слово»; кириллица по основе; `snake_case`/`camelCase` разбираются на слова. В выдаче — раздел и лучшая строка с номером |
| `grep ШАБЛОН [-k 60]` (MCP: `grep`) | построчный поиск регулярным выражением по всем карточкам: каждая совпавшая строка как «карточка Lстрока: текст» и общий счёт. Нужен, когда требуются **все** вхождения (перечень, разбросанный по репликам, счёт упоминаний): `find` отдаёт только лучшую строку каждой карточки |
| `open ID [--section N \| --lines a-b \| --full]` | карточка: маленькая целиком, большая — оглавлением; вывод ограничен (~3K токенов), хвост подсказывает, как продолжить |
| `patch ID --version N --old … --new …` | замена ровно одного вхождения. Версия устарела или файл изменили мимо картотеки → `STALE` и свежий текст вокруг цели, ничего не записано |
| `fact КЛЮЧ ЗНАЧЕНИЕ` · `facts` · `fact-history КЛЮЧ` · `retract КЛЮЧ` | журнал фактов: новое значение заменяет старое, история хранится |
| `set-summary` · `set-group` | переписать подписи каталога (человеком или дешёвой моделью-«библиотекарем»), тексты карточек не трогаются |
| `refresh` | обновить индекс по [`project.json`](project.json): код (по хэшу), объекты стола, экспорты чата только если файл изменился (подписи «библиотекаря» не затираются) |
| `canon [--types …]` | **канон стола**: факты и решения, которые человек принял (`ACCEPT`); у пересмотренного (`SUPERSEDE`) пометка `(replaces D001: причина)`. База стола открывается только на чтение |
| `promote КЛЮЧ [--apply] [--accept]` | предложить факт журнала столу: объект `raw` через штатную `pm.py add`. По умолчанию пробный запуск; `--accept` (принять сразу) — решение человека, в MCP его нет; запись из MCP разрешает `promote.mcp_apply` |
| `handoff [--budget N]` | стартовая справка новой сессии: правила памяти + канон + действующие факты + список групп (≈2K токенов) |
| `note ЗАГОЛОВОК ТЕКСТ --source КАРТОЧКА:СТРОКИ[:ЦИТАТА]` | **заметка с проверяемыми источниками** («вики»): при записи проверяется, что карточка есть, строки в её пределах и цитата найдена дословно (с точностью до регистра, кавычек и разметки); слепок строк хранится, поэтому потом видно, что источник изменился. Заметку можно править `patch` (версии), она ищется `find` наравне с картотекой. Из MCP — инструмент `note`, источники обязательны (`notes.require_sources`), запись можно выключить (`notes.mcp_write`) |
| `lint [--today ГГГГ-ММ-ДД]` | проверка здоровья памяти **без модели**: канон стола с датой в прошлом или условием «пока…»; факты журнала без источника; предложения столу, которые висят без `ACCEPT`; канон, отставший от журнала (с готовой командой `SUPERSEDE`), и журнал, отставший от канона (стол заменил объект, а журнал держит старое: `ledger-behind-canon`); заметки без источника, с пропавшим или изменившимся источником, с ненайденной цитатой, с битой ссылкой `[[nNNN]]`. Код возврата 1, если есть ошибки; одна строка итога попадает в `handoff` |
| `log [-n 20] [--grep X]` | журнал операций (факты, заметки, правки, предложения столу) вместе с событиями стола: строки `## [дата время] операция \| предмет \| подробности`, читаются обычным `grep` |
| `export-wiki ПАПКА` | заметки как папка markdown в духе «LLM Wiki» (`index.md`, `log.md`, `pages/`); ссылки `tNNN L12-30` дополняются координатами файла чата. База остаётся источником истины, папка — генерируемый вид (как `STATUS-FROM-DB.md` у стола) |
| `serve [--refresh]` | MCP-сервер по stdio с теми же инструментами; правила памяти едут в поле `instructions` |

Тексты, которые видит модель (выдача и описания инструментов), по-английски: меньше токенов. Документация и комментарии — по-русски.

### Быстрый старт

```bash
cd engine/cards
python3 cards.py refresh                          # код + объекты стола + чаты из attachments/ → engine/cards/cards.sqlite (≈4 с первый раз)
python3 cards.py catalog --level 1
python3 cards.py find parse_neq_title             # → engine/pm.py, L337
python3 cards.py open t010                        # маленькая реплика — целиком
python3 cards.py fact budget "96000 EUR" --source "реплика 8"
python3 cards.py canon                            # что человек принял на столе
python3 cards.py promote budget --apply           # предложить столу: объект raw, принять должен человек
python3 cards.py handoff                          # справка для новой сессии
python3 cards.py lint                             # что в памяти протухло (канон, журнал, заметки)
python3 -m unittest test_cards.py                 # 52 теста, без сети; реальная база стола в тестах не трогается
```

Отдельные индексаторы (`index-code`, `index-chat`, `index-pm`) остались для случаев вне проекта.

### Подключение к Claude Code

В корне репозитория лежит [`.mcp.json`](../../.mcp.json): Claude Code при первом запуске спросит разрешения и сам поднимет сервер
(`cards.py --db engine/cards/cards.sqlite serve --refresh` — база собирается при старте, пути относительные). Правила памяти приходят вместе с сервером в
`instructions`, подсказывать названия инструментов в запросе не нужно.

Не включено: пример хука `SessionStart`, который кладёт справку в начало каждой новой сессии, — [`hooks.example.json`](hooks.example.json)
(скопировать в `.claude/settings.json`, если нужен такой режим).

**Три сессии подряд в настоящем Claude Code** (подробно — [`eval/RESULTS.md`](eval/RESULTS.md), раздел 5): первая записала поправки в журнал и предложила
столу факт; вторая — новый процесс без истории — сама вызвала `canon` и `facts` и ответила верно, различив «принято на столе» и «только в журнале»;
третья получила справку хуком, без инструментов, за один ход и ≈3.6K токенов на входе. Без моста та же сессия отвечает, что ничего не знает.

## Как это стыкуется с комплектом

`pm.py` — это и есть «стол»: sqlite с каноном, команды вместо прозы (`LOOK`, `PLANT`, `ACCEPT`…). Картотека не заменяет его, а даёт то же
для материала, который в стол не влезает: 4.7 МБ экспорта чата (≈1.3 млн токенов) или код репозитория.

| стол (`pm.py`) | картотека |
|---|---|
| `PLANT` — посадить сырьё | `index-chat`, `index-code`, `refresh` |
| `LOOK` — срез по множествам | `catalog`, `find` |
| `ACCEPT` / `canon` — зафиксировать вывод | читаем `canon`; предлагаем `promote` (raw), принимает человек |
| `DUMP` / `JSON` — снимок для следующего агента | `handoff` — стартовый промпт новой сессии |

Журнал фактов — тот же приём, что `canon`, но для самой беседы: поправка не перезаписывает прошлое молча, а становится новой версией;
в промпт идёт только срез «действует».

### Конвейер: факт беседы → стол → канон → следующая сессия

```
пользователь поправил → fact_set (журнал, версия +1)      ← быстро, агент пишет сам, история хранится
                         │
                         ▼  promote (по решению агента или человека)
                 объект raw в столе (pm.py add)             ← предложение, не канон
                         │
                         ▼  ACCEPT — только человек
                 канон стола (pm.py)                        ← долговечно, выше журнала при расхождении
                         │
                         ▼  handoff / canon
              следующая сессия начинает с канона + журнала
```

Картотека читает базу стола в режиме `ro` и пишет в неё только его собственной командой `add`. Агент не может принять факт в канон
(в MCP нет `accept`), а запись `raw` через MCP по умолчанию выключена (`promote.mcp_apply: false` в [`project.json`](project.json)): база стола лежит
в репозитории, и менять её молча не должен никто. Агент покажет, что было бы записано, и подскажет человеку команды; включить запись — одной строкой в конфиге.

Принятое снять нельзя (`TAKE` отказывается от канона), его **заменяют**: новая версия факта становится новым объектом (`LF-ключ-v2`), и человек выполняет
`python3 pm.py exec SUPERSEDE LF-ключ-v1 BY LF-ключ-v2 причина`. Старый объект получает статус `superseded` и уходит из канона, новый принимается в той же
транзакции, связь `новый -supersedes-> старый` и причина остаются в истории, откат — `SUPERSEDE LF-ключ-v1 UNDO`. `promote` и `lint` подсказывают эту команду,
`canon` помечает пересмотренное решение, карточки стола пишут «superseded by …». В MCP глагола нет: решает человек.

## Измерения

Подробно, с таблицами и оговорками: [`eval/RESULTS.md`](eval/RESULTS.md). Повтор — по [`eval/README.md`](eval/README.md).
Агент — основная модель (журнал фактов — малая модель того же семейства; идентификаторы задаются переменными `EVAL_MODEL` и `EVAL_MODEL_SMALL`), материал — 96 файлов этого репозитория (≈240K токенов) и экспорт чата в 4.7 МБ (≈1.3 млн токенов).

| что проверяли | итог |
|---|---|
| весь корпус в промпте против поиска | на репозитории те же 26 ответов стоят $1.60 против $0.06–0.14; чат так не поддаётся вообще |
| каталог в первом сообщении | окупается на вопросах «по смыслу» (1.0 вызова на вопрос вместо 2.1, цена вдвое ниже), не окупается на вопросах по точным словам (`Grep` дешевле) |
| картотека против обычного `Grep` на чате | та же точность (62/62), цена в пределах разброса ($0.59–0.71 против $0.67). **Выигрыша здесь нет** |
| «библиотекарь» (подписи каталога от дешёвой модели) | для сырого файла −34% к цене; для карточек не помог |
| журнал фактов против ленты и `/compact` | 90/90 и 60/60 против 89/90 и 59/60 у ленты; токенов в 14–36 раз меньше; деньги в 1.5–13 раз меньше; по времени ≈3× дольше. `/compact` теряет счёт поправок и собственные выдумки (5/9 и 6/9) |
| правка при чужой правке | встроенный `Edit` и `patch` справились оба (3/3); `patch` строже и тратит один лишний вызов |
| вопросы на синтез по 2–3 репликам (17 проверенных) | `Grep` по сырому чату 96%; картотека с `find`/`open` 76%; та же картотека с `grep` по строкам 96% и на 27% дешевле ($0.041 против $0.056 за вопрос), быстрее и с меньшим числом вызовов |
| заметки-«вики» (Карпати) поверх чата | точность не поднимают: «вики-файлы + `Grep`» 98% против 96% у `Grep` (шум), заметки к картотеке 86% против 76% (по этим данным от шума не отличить); агенты в вики почти не заходят (9 ходов из 51). Вики без сырого текста: 0/34 — в заметки попало 36% нужных фактов; со вторым сжатием (дословные перечни, 72% фактов, втрое больше заметок) 6/34 и в три раза дороже поиска по тексту |
| верность заметок (выборка, судья-модель) | утверждения подтверждены полностью в 89% (ДИ 81–94%); обзоры страниц без неподтверждённых утверждений в 71% (ДИ 51–85%) — слабее всего слой синтеза |

Коротко: главный выигрыш даёт не картотека, а то, что корпус **не лежит в промпте**, а агент его ищет. Картотека добавляет то, чего поиск не даёт:
журнал фактов с версиями (память беседы без перечитывания), правки с проверкой версии, историю только для чтения и общий «снимок» для следующей сессии.
Отдельно: построчный `grep` по карточкам (иначе на вопросах «собери всё про X» она слабее обычного `Grep`) и `lint`, который находит в памяти устаревшее без модели.
Идея «LLM Wiki» на этом корпусе и этих вопросах выигрыша в точности не дала (подробности — раздел 6 в `RESULTS.md`).

## Что не сделано

- Нет векторного поиска: смысловые запросы агент переформулирует сам (как в Claude Code). Для многоязычных архивов с синонимами это слабое место.
- Подписи каталога для чата строятся эвристикой (вопрос + заголовки ответа). Их качество определяет, насколько каталог помогает; `eval/label_catalog.py`
  показывает, как переписать их дешёвой моделью (для карточек это в измерениях не помогло).
- Несколько процессов (по серверу на сессию) делят одну базу через WAL и `busy_timeout`; очереди записи и блокировок на уровне фактов нет — при одновременной записи
  одного ключа выигрывает последний.
- Карточки-реплики чата и копии объектов стола только для чтения (`patch` отказывает): история не правится, выводы записываются в журнал фактов.
- Замену принятого (`SUPERSEDE`) выполняет только человек: картотека подсказывает команду и замечает расхождение, но сама не заменяет. Снять канон без заместителя по-прежнему нечем (заместителем может быть объект «отменено»); у защиты от опечатки в id нет понимания смысла: она смотрит на связь, тип и общие слова заголовков.
- `lint` проверяет механику (даты, источники, цитаты, ссылки), а не смысл: противоречий между заметками или между журналом и каноном по существу он не ищет.
- Заметки пишутся пока только одним проходом малой модели (`eval/compile_notes.py`) или агентом через `note`; обновления вики при изменении чата (какие страницы пересобрать) нет — лишь пометка `lint`, что источник изменился.

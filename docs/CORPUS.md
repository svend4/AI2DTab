# Корпус: что намерили до и после v2.1

Проверка нарезчика и классификатора движка (`src/engine/plant.ts`,
`src/engine/cells.ts`) на единственном настоящем корпусе проекта. Все цифры
ниже скопированы из вывода скрипта, команда указана при каждой таблице.
Воспроизведение:

```sh
node --experimental-strip-types scripts/corpus-stats.mjs --mode auto
node --experimental-strip-types scripts/corpus-stats.mjs --mode paragraph
node --experimental-strip-types scripts/corpus-stats.mjs docs/corpus/sample.json --no-gold
```

Скрипт печатает один JSON: статистику корпуса (`corpus`), сравнение с
золотой разметкой (`gold`, по умолчанию `docs/corpus/gold.json` +
`docs/corpus/sample.json`) и цифры «до» (`before`, из
`docs/corpus/baseline.json`). Полный прогон по 4,7 МБ занимает ~1,5 с.

## 1. Что за корпус

`attachments/ChatGPT_2026_09_18__1900.md` — экспорт одного диалога с ChatGPT:
4 747 159 байт, 344 396 строк, 81 ход пользователя и 81 ответ (162 маркера
`# you asked` / `# chatgpt response`). 70 ходов пользователя — «Да» (51) или
«Продолжение» (16) и их варианты. 94,9 % строк (326 761 из 344 396) начинаются с `>`: экспорт
обернул весь текст в блок-цитаты, и нарезчик v2.0 этого не понимал. Внутри —
«Innovation OS»: 32 035 нумерованных заголовков `# N. Заголовок`, 29 472
различных номера (2 563 номера повторяются с другим содержанием).

## 2. Нарезка: до и после

«До» — две строки из `baseline.json`: нарезчик v2.0 как есть (без снятия
цитат) и прототип «снять `>` и линии, затем нарезать по абзацам» — тот же
алгоритм, из которого набирали выборку для разметки. «После» — движок v2.1:
`--mode auto` выбирает режим секций (нумерованных заголовков ≥ 20), для
сравнения дан и `--mode paragraph`.

| Метрика | v2.0 как есть | v2.0 + снятие цитат | v2.1 `auto` (= секции) | v2.1 `paragraph` |
|---|---|---|---|---|

| Секций распознано | 0 | 32 035 (по заголовку) | 32 035 | 0 |

| Длина p50 / p90 | — | 31 / 66 | 82 / 178 | 43 / 92 |

Что изменилось в нарезчике и что это дало:

- **Снятие `>`** — главный выигрыш: без него весь диалог был 4 965 кусков с
  p99 в 36 тыс. символов, то есть целые ответы модели как один «абзац».
- **Режим секций** — блок = заголовок + тело до следующего заголовка. Коротких
  обрывков 331 вместо 27 222, и почти все они — ходы «Да»/«Продолжение» (51 +
  16), а не ярлыки «Например:». Цена: p99 длины вырос до 504 и max до 2 763,
  и ячейки внутри тела секции с «настоящим» заголовком не всплывают в
  заголовок записи — поэтому ячеек 803 против 1 434 в режиме абзацев.
  Разница (~630) — ячейки, которые лежат в теле и ждут `FILL`/`WHY`, а не
  потеря.
- **Склейка «ярлык + кодовый блок»** работает в режиме абзацев: из 70 блоков,
  которые судьи пометили `merge_with_prev`, 50 (71 %) склеены с соседом, 20
  остались отдельными. В режиме секций все 70 оказались внутри секций
  (`merged_share` = 1,0) — склейка там тривиальна.
- **Повторы номеров**: 2 563 секции с уже встречавшимся номером получили id
  `S{N}-2`, `-3`… вместо молчаливого пропуска; 74 блока с ровно тем же текстом
  (повторные «Да») свёрнуты в один id.

Короткие блоки, оставшиеся в режиме секций (из вывода `top_short`): «Да» 51,
«Продолжение» 16, «Вместо:» 2, «Или:» 2 — дальше единичные.

## 3. Классификатор: точность и полнота по типам

Выборка: 200 блоков прототипной нарезки (140 длиной ≥ 24 символов, 60 коротких,
детерминированная выборка), размечены тремя LLM-судьями, тип — большинством
голосов. Распределение золота: observation 60, label 78, code 54, decision 4,
question 2, task 2; `noise` не встретился ни разу. Единогласных по типу — 144
из 200 (72 %).

«после» — тот же прогон `--mode auto` (`gold → per_type`).

гранулярности разметки и нарезчика, а не ошибка классификатора — см. §6. Если
эти 32 убрать, остаётся 12 содержательных ошибок на 168 блоков (0,93).

## 4. Десять худших оставшихся ошибок и правило для каждой

Отсортировано: сначала единогласные у судей, затем длинные тексты (поле
`gold → worst`, запуск с `--worst 44`). Для правил даны цифры по всему корпусу,
полученные разовыми проверками поверх того же нарезчика.

По корпусу (режим абзацев) из 3 556 блоков-в-ограде таких 800 однострочных и ещё 121 многострочных из одних прозаических строк; «кодом» выглядят 2 540. |

Пропущенные ячейки (3 из 8 в золоте) — отдельный класс: «Procedures themselves
могут быть packages.» (судьи: `Procedures ⊂ packages`), «verifier must not be
same as builder» (`verifier ≠ builder`), `# 15289. Execution Placement is
therefore specialized capability matching.` (`… ⊂ …`). Это ячейки, записанные
естественным языком без оператора; правило «`могут быть` / `is therefore` → ⊂,
`must not be same as` → ≠» вытащит их, но даст ложные срабатывания — лучше
оставить человеку через `FILL`, чем угадывать. Единственная ложная ячейка —
`bad results → invest more only because already invested`, где и судьи
разошлись 1 к 2.

## 5. Что это значит для анализа стадии

- Идея «лента → адресуемые записи» теперь **проверена на собственном корпусе
  инструментально**, а не на глаз: 344 тыс. строк → 32 965 секций с
  устойчивыми id, 803 ячейки на уровне заголовков (2,4 % секций) и ещё ~630 в
  телах; `≠` остаётся главным отношением (567 из 803), что подтверждает ставку
  v1 на различение как первичную грамматику.
- Классификатор поднялся с 0,30 до 0,78 по типу (0,94 на единогласных
  блоках), ячейки — с полноты 0,50 до 0,63 при точности 0,83. Это уровень
  «предпросмотр посадки читаем», не «можно сажать без человека»: 15 % блоков
  observation и 42 % ярлыков всё ещё размечены иначе, чем судьи.
- Перейти на следующую ступень (`docs/STAGE.md`, §1) это не позволяет:
  корпус один, автор один, судьи — модели. Остаются неизмеренными: второй
  корпус другого человека; человеческая разметка вместо модельных судей;
  согласие между судьями как метрика (сейчас известно только число
  единогласных: 144 из 200 по типу, `baseline.json → gold_summary.unanimous`);
  выигрыш в работе (доля «Да»-ходов, время до первого канона).

## 6. Пределы этого измерения

1. **Судьи — три LLM, не люди.** Большинство из трёх моделей — это согласие
   моделей, не истина; на 56 из 200 блоков судьи расходились.
2. **Выборка 200**, стратифицированная (140 длинных / 60 коротких), не
   взвешенная по корпусу: редкие типы представлены 2–4 примерами, и их P/R
   (`question`, `task`, `decision`) ничего не значат статистически.
3. **Золото размечено на абзацных блоках прототипа, а нарезчик v2.1 режет
   секциями.** Отсюда 32 «ошибки» `label → observation` на голых заголовках: в
   секционном виде у них есть тело, и правильный тип другой. Честная проверка
   секционного режима требует переразметки на секциях.
4. Тексты в `sample.json` обрезаны до 1 500 символов; прототип снимал `>` по
   шаблону `^(>\s?)+`, движок — `^(\s*>\s?)+`; на выборку это не повлияло
   (все 200 блоков найдены в новой нарезке), но при повторном наборе выборки
   стоит резать движком.
5. Прогон скрипта на `docs/corpus/sample.json` как на корпусе (склейка 200
   текстов) даёт 70 секций: `auto` видит 70 нумерованных заголовков и
   прячет 130 остальных блоков в их тела — показательно для правила «≥ 20
   заголовков → секции» и его слабого места на смешанных текстах.

Файлы: `scripts/corpus-stats.mjs` (скрипт), `docs/corpus/gold.json` (золото,
200 блоков, 3 судьи), `docs/corpus/sample.json` (тексты выборки и догадка
классификатора v2.0), `docs/corpus/baseline.json` (цифры «до»).

# Стол v2 — мой вариант

Ветка `ccr-16458c8b-rhgxsh`. Тот же замысел (лента → плоскость → канон →
действие, канон ставит человек, машина ходит по id), другая реализация и
несколько новых идей. Ниже: что изменено, почему, плюсы/минусы, спорные
места и куда двигаться дальше.

## 1. Принципы v2

1. **Один движок, один источник истины.** `src/engine/` — чистые функции над
   JSON-книгой `{objects, links, origins, events}`. Нет python-субпроцесса,
   нет sqlite, нет `/workspace`, нет второго классификатора в UI. Движок
   одинаково работает в браузере, в Node и в тестах.
2. **Тот же язык.** Все глаголы v1 сохранены с той же семантикой (`PLANT
   ACCEPT TAKE FILL SWEEP PURGE REPAIR SET NEQ CONC VOCAB GRID DIFF PACKET WIRE
   PROBE PORT INSTR GAP SETTLE RUN FETCH SPEC JSON DUMP BATCH`). Формульный
   синтаксис `=COUNTIF(≠)`, `=PIVOT` тоже. Книгу v1 (`seed.sql`, `DUMP`-TSV)
   v2 читает без конвертации.
3. **Каждая запись обратима.** Событие хранит `before/after`; `UNDO` откатывает
   ACCEPT, TAKE, PLANT, GAP, SETTLE, WIRE, UNWIRE. Откат сам остаётся в журнале
   — SPEC его видит.
4. **Правила как данные.** Пороги приборов, предупреждения и вопросы-GAP —
   таблица `RULES` в `instruments.ts`. `NEXT` ничего не знает про конкретные
   id, только про формы: «открытый ярлык в C», «dormant signpost с ребром
   triggers», «ребро contradicts/blocks», «raw ячейки ждут FILL».
5. **Посадка объяснима и идемпотентна.** id = префикс типа + хеш
   нормализованного абзаца. Один абзац → один id всегда; разные абзацы не
   сталкиваются. На L1 — сухая посадка: таблица «id / кластер / тип / почему /
   заголовок» до записи.
6. **Хранение без аккаунтов.** Книга в `localStorage`, перенос — экспорт/импорт
   JSON. По §0.5 `AGENTS.md` auth/db выключены: это одиночный стол. Сервер
   появится только при явном запросе на общий стол.

## 2. Что нового (по сравнению с v1)

| Область | v1 | v2 |
|---|---|---|
| Грамматика ячейки | только `≠` | `≠ → ⊂ = vs`, юникод и ASCII (`!=`, `->`, `is-a`, `против`) |
| Ячейка в теле | нет | `Critical invariant:\n```Ontology ≠ Policy```` → заголовок берётся из тела |
| Алгебра множеств | один оператор | полное выражение: `NEQ ∩ (RAW ∪ CANON) \ C`, фильтры `type:question`, `status:raw`, `has:link`, `rel:→` |
| Идентификаторы | порядковые, сталкиваются | хеш содержимого, стабильные |
| Нарезка | по пустой строке | + заголовки markdown, кодовые блоки не рвутся |
| Откат | REPAIR по эвристике | UNDO по журналу |
| NEXT | три зашитых id | правила над формой книги |
| Приборы | 4 порога в коде | 6 правил-данных, + «сироты канона», «вопросы копятся» |
| WHY | нет | объяснение любой строки: ячейка, рёбра, происхождение, журнал |
| Граф рёбер | таблица from/rel/to | SVG: кластеры-колонки, подсветка соседей, клик → WHY |
| WIRE из UI | только строкой | форма с автодополнением id + PROBE-кандидаты в один клик |
| Пачка | строка BATCH | чекбоксы в таблице → BATCH ACCEPT/TAKE |
| Матрица L2 | тип × кластер | статус × кластер, клик режет срез |
| Протокол агента | устно в CHAT-CRUTCH.md | блок на L4 + `docs/PROTOCOL.md` + `JSON`-снимок |
| Перенос | sqlite-файл | экспорт/импорт JSON и TSV |
| Деплой | только песочница Grok | статический SPA, Vercel/любой хостинг |
| Тесты | 0 | 10 сценариев движка, включая воспроизведение багов v1 |
| «Четыре такта» | мёртвый код | маршрут `/cycle` |

## 3. Плюсы и минусы v2 (честно)

**Плюсы.** Запускается где угодно; быстрее (нет субпроцесса на каждый ход);
поведение проверяемо тестами; одна реализация языка; каждое действие
объяснимо (WHY) и обратимо (UNDO); книга переносима между агентами как JSON.

**Минусы и цена.**
- Потерян Python-CLI как «второй вход» в ту же базу. Если он нужен — это
  ~150 строк обёртки над `engine/` через Node, не второй движок.
- `localStorage` ≈ 5 МБ. Корпус на 30 тыс. секций туда не влезет целиком;
  для него нужен IndexedDB или сервер. Семя и комплект (31 + 36 строк)
  занимают килобайты.
- Хеш-id (`C-k3f9a1`) хуже читается, чем `S17042`. Компромисс: секции с
  номером (`# 17042. …`) сохраняют свой номер.
- Классификатор остался эвристическим. Он объясняет себя («почему»), но его
  точность не измерена — нужен размеченный набор из 200–300 абзацев.
- Пороги приборов перенесены как есть (0.2 / 0.45 / 0.4 / 8). Они стали
  данными, но не стали обоснованными.

## 4. Спорные места (дискуссия)

**Канон ставит только человек — а что делает модель?** В v1 и v2 модель
может PLANT, SET, PROBE, GAP, FETCH, но ACCEPT формально доступен ей тоже.
Предлагаю правило статусов: `machine:*` не имеет права на `raw → canon`;
только `human`. В движке это одна проверка по полю `owner` события — не
сделано намеренно, пока не решено, кто именно нажимает кнопки на столе.

**Кластеры A/B/C/D — это что?** В семени: A = Enbek (внешний проект),
B = технопарк (свой проект), C = Innovation OS (корпус текстов),
D = foresight (наблюдения/сигналы). То есть не одна ось, а смесь
«проект / источник / горизонт». Запрет MUL интуитивно про это: нельзя
перемножать проект с корпусом. Нужно назвать ось явно; иначе «перекос C»
просто означает «вы посадили большой текст».

**`≠` как первичная грамматика.** Сильная идея (различение раньше
определения), но корпус Innovation OS даёт 11 ячеек на 36 секций — остальное
«Critical invariant:» + тело. v2 вытаскивает ячейку из тела, и это даёт ещё
несколько. Дальше нужен ручной заголовок: ячейка — это работа человека, а
не regex.

**Заряд = canon/(raw+canon).** Метрика растёт и от ACCEPT, и от TAKE (TAKE
убирает raw из знаменателя). То есть «вычесть всё лишнее» поднимает заряд так
же, как «принять нужное». Возможно, это и задумано (ёмкость чистится), но
стоит назвать явно или считать `canon/(raw+canon+rejected)`.

## 5. Новые идеи (не реализованы, предлагаю)

1. **Права по ролям в журнале.** `owner` уже есть у объектов и `actor` у
   событий. Правило «machine не делает canon» + отчёт «сколько раз модель
   пыталась» — это и есть измеримый эффект стола.
2. **Два стола — один протокол.** Агент A получает `JSON`-снимок, делает
   PLANT/PROBE/GAP, отдаёт `JSON`; агент B продолжает. Нужен один
   дополнительный глагол `MERGE` (по хеш-id он тривиален: одинаковые абзацы
   совпадут сами).
3. **Диф двух книг.** `DIFF book1 book2` → что принято/вычтено/добавлено —
   основа для ревью канона вторым человеком.
4. **Шкала уверенности классификатора.** Выдавать не только «почему», но и
   «насколько»; всё ниже порога — в отдельный срез «спорная посадка».
5. **Ячейка с направлением.** `→` уже есть; следующий шаг — `WIRE` сам
   предлагает ребро, если `obj` одной ячейки совпадает с `pred` другой
   (цепочки A ≠ B, B → C).
6. **Таймлайн канона.** События имеют `ts`; срез «что было каноном на дату»
   даёт честный ответ на «учти прошлую сессию» без контекста модели.
7. **MCP-инструмент.** Алфавит — готовая поверхность для любого агента: один
   инструмент `desk.exec(line)` + `desk.snapshot()`. Это делает стол
   инструментом модели, а не сайтом рядом с ней.

## 6. Дорожная карта

- **v2.2**: общий стол (auth ON по §0.5: аккаунты, `authMiddleware`, Postgres);
  `DIFF` книг; таймлайн канона.
- **v3**: MCP-сервер над движком; второй корпус от другого автора; замер

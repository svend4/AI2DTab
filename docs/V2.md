# Стол v2 — мой вариант

Ветка `ccr-16458c8b-rhgxsh`. Раздел 7 — что изменилось в v2.1 после встречного
ревью и эксперимента на корпусе. Тот же замысел (лента → плоскость → канон →
действие, канон ставит человек, машина ходит по id), другая реализация и
несколько новых идей. Ниже: что изменено, почему, плюсы/минусы, спорные
места и куда двигаться дальше.

## 1. Принципы v2

1. **Один движок, один источник истины.** `src/engine/` — чистые функции над
   JSON-книгой `{objects, links, origins, events}`. Нет python-субпроцесса,
   нет sqlite, нет `/workspace`, нет второго классификатора в UI. Движок
   одинаково работает в браузере, в Node и в тестах.
2. **Тот же язык.** Все глаголы v1 сохранены (`PLANT ACCEPT TAKE FILL SWEEP
   PURGE REPAIR SET NEQ CONC VOCAB GRID DIFF PACKET WIRE PROBE PORT INSTR GAP
   SETTLE RUN FETCH SPEC JSON DUMP BATCH`), множества `NEQ`/`JUNK` считаются
   как в v1 (см. §7). Формульный синтаксис `=COUNTIF(≠)`, `=PIVOT` тоже. Семя
   v1 (`seed.sql`) лежит в репозитории как `src/data/seed.json` с полями
   sqlite; `normalizeBook` переводит их при загрузке, включая письма `packets`.
   Отличия, которые остались намеренно: GRID показывает третий счётчик для
   прочих статусов; BATCH останавливается на первой ошибке (v1 — тоже, но
   с падением процесса); классификатор посадки другой (§7).
3. **Каждый ход обратим.** Событие хранит `before/after` и номер хода; `UNDO`
   откатывает последний ход целиком (FILL на 11 строк, BATCH, многострочный
   PLANT). Откаченные события остаются в журнале с пометкой `undone` — SPEC
   считает живые и откаченные отдельно.
4. **Правила как данные.** Пороги приборов, предупреждения и вопросы-GAP —
   таблица `RULES` в `instruments.ts`. `NEXT` ничего не знает про конкретные
   id, только про формы: «открытый ярлык в C», «dormant signpost с ребром
   triggers», «ребро contradicts/blocks», «raw ячейки ждут FILL».
5. **Посадка объяснима и идемпотентна.** id = префикс типа + хеш
   нормализованного абзаца. Один абзац → один id всегда; разные абзацы не
   сталкиваются. На L1 — сухая посадка: таблица «id / кластер / тип / почему /
   заголовок» до записи.
6. **Хранение без аккаунтов.** Книга в IndexedDB (откат на localStorage),
   результат каждого сохранения виден в шапке: где лежит, сколько весит, что
   пошло не так. Перенос — экспорт/импорт JSON. По §0.5 `AGENTS.md` auth/db
   выключены: это одиночный стол. Сервер появится только при явном запросе на
   общий стол.

## 2. Что нового (по сравнению с v1)

| Область | v1 | v2 |
|---|---|---|
| Грамматика ячейки | только `≠` / `!=` | `≠ → ⊂ = vs`, юникод и ASCII (`!=`, `->`, `is-a`, `против`); без квадратичных regex |
| Ячейка в теле | нет | `Critical invariant:\n```Ontology ≠ Policy```` → заголовок берётся из тела |
| Алгебра множеств | один оператор | полное выражение: `NEQ ∩ (RAW ∪ CANON) \ C`, фильтры `type:question`, `status:raw`, `has:link`, `rel:→` |
| Идентификаторы | порядковые, сталкиваются | хеш содержимого, стабильные |
| Нарезка | по пустой строке | + заголовки markdown, кодовые блоки не рвутся |
| Откат | REPAIR по эвристике | UNDO по журналу |
| NEXT | три зашитых id | правила над формой книги |
| Приборы | 4 порога в коде | 6 правил-данных, + «сироты канона», «вопросы копятся» |
| WHY | нет | объяснение любой строки: ячейка, рёбра, происхождение, журнал |
| Граф рёбер | таблица from/rel/to | SVG: кластеры-колонки, подсветка соседей, клик → WHY |

| Пачка | строка BATCH | чекбоксы в таблице → BATCH ACCEPT/TAKE |
| Матрица L2 | тип × кластер | статус × кластер, клик режет срез |
| Протокол агента | устно в CHAT-CRUTCH.md | блок на L4 + `docs/PROTOCOL.md` + `JSON`-снимок |

| «Четыре такта» | мёртвый код | маршрут `/cycle` |

## 3. Плюсы и минусы v2 (честно)

**Плюсы.** Запускается где угодно; быстрее (нет субпроцесса на каждый ход);
поведение проверяемо тестами; одна реализация языка; каждое действие
объяснимо (WHY) и обратимо (UNDO); книга переносима между агентами как JSON.

**Минусы и цена.**
- Потерян Python-CLI как «второй вход» в ту же базу. Если он нужен — это
  ~150 строк обёртки над `engine/` через Node, не второй движок.
- Корпус на 32 тыс. секций — это ~13 МБ JSON. IndexedDB его держит, но
  каждый ход сериализует книгу целиком (сотни миллисекунд); таблицы режутся
  по 200 строк. Для корпусов больше ~100 тыс. записей нужен сервер.
- Хеш-id (`C-k3f9a1zq0p`) хуже читается, чем `S17042`. Компромисс: секции с
  номером (`# 17042. …`) сохраняют свой номер, а на реальном корпусе таких
  93%.
- Классификатор остался эвристическим. Он объясняет себя («почему»), и в
  v2.1 его точность измерена на 200 абзацах с разметкой трёх судей-моделей
  (`docs/CORPUS.md`) — это не человеческая разметка.
- Пороги приборов перенесены как есть (0.2 / 0.45 / 0.4 / 8). Они стали
  данными, но не стали обоснованными.

## 4. Спорные места (дискуссия)

**Канон ставит только человек — а что делает модель?** В v2.1 это правило
исполняется: `ACTOR machine` переключает стол, после чего `ACCEPT`/`FILL`
отвечают `REFUSE … machine cannot canon`, а отказ пишется в журнал с актором.
Открытым остаётся вопрос доверия: переключатель нажимает тот же человек, так
что это дисциплина, а не защита. Защитой оно станет, когда агент ходит через
свой канал (MCP), а не через ту же страницу.

**Кластеры A/B/C/D — это что?** В семени: A = Enbek (внешний проект),
B = технопарк (свой проект), C = Innovation OS (корпус текстов),
D = foresight (наблюдения/сигналы). То есть не одна ось, а смесь
«проект / источник / горизонт». Запрет MUL интуитивно про это: нельзя
перемножать проект с корпусом. Нужно назвать ось явно; иначе «перекос C»
просто означает «вы посадили большой текст».

**`≠` как первичная грамматика.** Сильная идея (различение раньше
определения), но корпус Innovation OS даёт 11 ячеек на 36 секций — остальное
«Critical invariant:» + тело. v2 вытаскивает ячейку из тела, и это даёт ещё
несколько. Дальше нужен ручной заголовок: ячейка — это работа человека, а
не regex.

**Заряд = canon/(raw+canon).** Метрика растёт и от ACCEPT, и от TAKE (TAKE
убирает raw из знаменателя). То есть «вычесть всё лишнее» поднимает заряд так
же, как «принять нужное». Возможно, это и задумано (ёмкость чистится), но
стоит назвать явно или считать `canon/(raw+canon+rejected)`.

## 5. Новые идеи (не реализованы, предлагаю)

1. **Права по ролям в журнале.** `owner` уже есть у объектов и `actor` у
   событий. Правило «machine не делает canon» + отчёт «сколько раз модель
   пыталась» — это и есть измеримый эффект стола.
2. **Два стола — один протокол.** Агент A получает `JSON`-снимок, делает
   PLANT/PROBE/GAP, отдаёт `JSON`; агент B продолжает. Нужен один
   дополнительный глагол `MERGE` (по хеш-id он тривиален: одинаковые абзацы
   совпадут сами).
3. **Диф двух книг.** `DIFF book1 book2` → что принято/вычтено/добавлено —
   основа для ревью канона вторым человеком.
4. **Шкала уверенности классификатора.** Выдавать не только «почему», но и
   «насколько»; всё ниже порога — в отдельный срез «спорная посадка».
5. **Ячейка с направлением.** `→` уже есть; следующий шаг — `WIRE` сам
   предлагает ребро, если `obj` одной ячейки совпадает с `pred` другой
   (цепочки A ≠ B, B → C).
6. **Таймлайн канона.** События имеют `ts`; срез «что было каноном на дату»
   даёт честный ответ на «учти прошлую сессию» без контекста модели.
7. **MCP-инструмент.** Алфавит — готовая поверхность для любого агента: один
   инструмент `desk.exec(line)` + `desk.snapshot()`. Это делает стол
   инструментом модели, а не сайтом рядом с ней.

## 6. Дорожная карта

- **v2.1** (неделя): права по ролям; `MERGE`; IndexedDB вместо localStorage;
  размеченный набор для классификатора и его точность в README.
- **v2.2**: общий стол (auth ON по §0.5: аккаунты, `authMiddleware`, Postgres);
  `DIFF` книг; таймлайн канона.
- **v3**: MCP-сервер над движком; второй корпус от другого автора; замер
  «доля Да-ходов до/после».

## 7. v2.1 — что изменилось после встречного ревью

Ветку v2 проверили шесть независимых ревьюеров (движок, паритет с v1,
React/SSR, документация против кода, сами утверждения аудита, безопасность) —
75 находок, 14 из них по документации и 18 по самому аудиту (`docs/AUDIT.md`
§6). Исправлено в коде:

- **Паритет с v1 там, где я его нарушил молча.** `NEQ` снова только
  observation raw|canon (вычтенное не воскресало бы через `ACCEPT NEQ`);
  `ACCEPT NEQ ∪ x` отказывает не-ячейкам; `JUNK`/`PURGE` — только
  ярлыки-обёртки; `PORT` считает по `NEQ`; артикль снимается только у pred.
- **Идентификаторы.** `FETCH` сталкивал id в одну секунду (найдено четырьмя
  ревьюерами независимо) — теперь дата + время + развод суффиксом; хеш абзаца
  48 бит вместо 32 (ожидаемые коллизии на 30 тыс. абзацев: 2·10⁻⁶ вместо 19%);
  нормализация снимает markdown-маркеры только на границах слов (`re-use` и
  `reuse` — разные абзацы); коллизия с другим текстом разводится и
  сообщается, а не пропускается.
- **Откат.** `UNDO` — ход целиком; снимок хранит и штамп ячейки, так что
  откат `ACCEPT` не оставляет строку в `NEQ`; события остаются с пометкой
  `undone`; `REPAIR id` возвращает любую канон-строку в raw (раньше принятое
  по ошибке было навсегда).
- **Нарезка.** Однострочный ``` … ``` больше не открывает кодовый блок
  навсегда (это съедало всё после первого такого примера); блок-цитаты,
  горизонтальные линии и маркеры ходов; ярлык + кодовый блок — один блок;
  режим секций; `!=` внутри кода — не ячейка; `BATCH` не рвёт многострочный
  `PLANT`.
- **Приборы.** Вычтенные строки не входят в массу кластера и рёбра —
  кластер, который целиком вычли, не поднимает красную зону; `GAP` заново
  открывает закрытый вопрос, если правило снова живо; `hops` без прототипного
  загрязнения (импорт книги с кластером `__proto__` ломал `Object.prototype`).
- **Импорт.** `normalizeBook` на каждом входе: кластеры, статусы, id,
  зарезервированные имена (`RAW` как id принимал всё множество одним кликом),
  рёбра на отсутствующие записи; книга сохраняется только после того, как
  `refresh()` смог её отрисовать (раньше кривой импорт «окирпичивал» стол на
  следующей загрузке).
- **Хранение.** IndexedDB с откатом на localStorage и честным статусом
  сохранения: переполнение квоты раньше молча теряло всё после первого
  крупного PLANT.
- **UI.** Чтение без записи (`query`) в рендере; выбор строк сверяется с
  видимым срезом; пачка — по одному `exec` на id (сборка `BATCH` из id
  позволяла инъекцию глаголов через id с `;`); формы отключены до гидратации;
  предпросмотр с задержкой и срезом в 200 строк; WHY не устаревает.
- **Журнал.** Уплотняется после 5000 событий: старые сворачиваются в
  счётчики глаголов, SPEC их учитывает.

Что ревью подтвердило как спорное и что осталось как есть: `=` как отношение
принято с пробелами (`a = b`), но не `==`; `FETCH` теперь действительно
возвращает вопрос на ленту L1, а не только на плоскость; «деплой статическим
SPA» было неправдой — это SSR-приложение на Nitro, запись в таблице
исправлена.

Новое в v2.1 сверх исправлений: `ACTOR`, `MERGE`/`DIFFBOOK`, `CHAIN`,
`TURN`, секции и ходы диалога в происхождении, классы `code`/`label` в
классификаторе, эксперимент на корпусе (`docs/CORPUS.md`).

### 7.1 Второй круг ревью (на дифф v2.1)

Три проверяющих (движок, интерфейс, документация) по новому коду; 16
находок с воспроизведением. Закрыто:

- **Уплотнение журнала резало текущий ход.** После посадки корпуса на
  32 891 запись `UNDO` откатывал только 5000: лимит в 5000 событий
  срабатывал внутри самой посадки. Теперь уплотняются только события
  прошлых ходов, кроме последнего откатываемого.
- **MERGE приносил чужие номера ходов.** `UNDO` после слияния откатывал
  смесь своего и чужого хода с тем же номером. Чужая история теперь
  сливается без номеров ходов и снимков (её нельзя откатить, и это честно
  сказано: `UNDO` сразу после `MERGE` отвечает, что слияние не
  откатывается — сравнивайте экспорт, снятый до него).
- **Роль не переживала перезагрузку.** `ACTOR machine` писался в журнал, но
  стол после перезагрузки снова был «человеком». Конструктор восстанавливает
  роль из последнего непогашенного события `ACTOR`.
- **Чтение двигало ходы.** `query()` для рендера шёл через `exec` и
  увеличивал номер хода на каждую перерисовку; у движка появился `read()`
  без побочных эффектов, пишущие глаголы он отвергает.
- Посадка идемпотентна и после развода суффиксом (повтор того же текста
  больше не добавляет `S1-3`, `S1-4`…); `BATCH` не теряет английские строки
  продолжения; `normalizeBook` переназначает рёбра и происхождение на новые
  id и не даёт суффиксу дубликата вытеснить настоящий id; машина не
  поднимает канон ни через `MERGE`, ни через `UNDO`; откат `ACCEPT`
  снимает штамп ячейки; явные маркеры «Факт:/TODO:» идут раньше неявных
  решений, `Use of …` — не решение; `~~~` и тройной ``` на одной строке
  закрыты сами; id из TSV, совпадающий с именем множества, получает `-id`;
  вычтенное липкое при слиянии (поднимает только канон); рёбра к вычтенному
  не считаются живыми; `and-1` — это id, а не оператор.
